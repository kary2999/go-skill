## 🚨 ZERO STEP：生成前必做的门禁（任一失败拒绝生成）

### STEP 0-A · 跑 git 命令取改动

```bash
# 改了哪些文件
git diff --name-only origin/master...HEAD

# 完整 commit 信息（title + body），用于业务分析
git log origin/master..HEAD --format='%H%n%s%n%n%b%n---'

# 提测人：最新一条 commit 的作者（**不信任手填，以此为准**）
git log -1 --format='%an <%ae>'
```

记下结果。后面每一段都要能和文件清单对得上。

### STEP 0-E · 开发侧 3 步自验前置（**G8 门禁** · 不完成就别提测）

**规则来源**：提测前自验要求（通用）。任何一条失败 = 先修再提，不许带病提测。

#### 第一步：理解改动

1. 跑 `git diff origin/master...HEAD` 看所有代码改动
2. 结合需求描述，总结：
   - 这次**改了什么**
   - 影响了**哪个业务流程**
   - 在**什么环节**生效
3. 用**一段话**写出你的理解（复制进报告 §N「开发自验记录」→ 理解摘要）

> 这段话会同时进 QA 版 §1 开头，**测试同学据此确认你理解的和需求一致**。

#### 第二步：找到核心场景（最少数量，不穷举）

基于你的理解，回答以下 3 个问题，每个问题**只需 1 条场景**：

| 问题 | 要验证什么 | 场景示例 |
|---|---|---|
| **能生效吗？** | 改动在正确配置下按预期工作 | 开了优惠券开关 + 用户有券 → 下单自动抵扣 |
| **能关掉吗？** | 有开关/配置的，关掉后不影响原有流程 | 关闭优惠券开关 → 下单走原流程，无抵扣 |
| **边界在哪？** | 临界值行为明确且符合预期 | 券额度 = 订单金额 → 订单实付 0，状态正常 |

#### 第三步：在 dev 环境真跑

每条场景必须有：

```
场景：{场景名}
操作：{具体步骤}
结果：通过/失败
证据：{关键日志 / DB 记录 / 截图路径}
```

**任一场景失败 = G8 门禁 fail = 拒绝生成报告**。要么修完再提，要么把 "失败" 那条带着失败原因诚实填上让 QA 知情（不推荐，仅用于阻塞发布时）。

**G8 门禁**：
- ✅ 开发版 §N「开发自验记录」三小段都非空
- ✅ 3 条场景都有操作 + 结果 + 证据
- ❌ 任意场景"结果：失败"且未修复 → 拒绝生成（除非开发显式声明"已知失败，原因 XX，影响范围 YY，经 Z 同意带病提测"）

### STEP 0-D · 业务范围深度挖掘（**§1 业务改动必读**，G7 门禁）

这是最近一次用户反馈：**测试同学看不到具体业务是什么**。所以必须做这步。

**挖掘流程（严格按顺序）**：

1. **读所有 commit body**：`git log origin/master..HEAD --format='%H%n%s%n%n%b%n---'`
   - 提炼"做了什么（核心业务变化）" + "为什么（业务动机）"
   - commit title 里的 `feat:/fix:` 前缀是类型，后面才是业务
   - body 里可能有 JIRA 单号 / PR 描述 / "根因" 等关键信息
   - 忽略纯粹的 `chore:` / `refactor:` / `style:` commit（非业务）

2. **读改动文件的 godoc / 业务注释**：
   ```bash
   git diff origin/master...HEAD -- '*.go' '*.php' | head -2000
   ```
   - 找每个新增/修改函数上方的 `// 函数名 does xxx` godoc
   - 找**中文业务注释**（通常 `// 校验...` / `// 处理...` / `// 根据 ... 计算...`）
   - 函数级、类级的注释最有价值；行内注释通常是技术性的，次要
   - 引用时**保留原文 + 带文件路径和行号**作为证据（例：`internal/biz/order.go:45："校验优惠券有效性"`）

3. **按业务功能分组**：
   - 如果一个 PR 改了多个独立业务功能，**分别描述**（不要糊成一段）
   - 每组对应几个 commit + 几个文件 + 几段注释

4. **业务动机提炼**：
   - 首选：JIRA/PRD 链接（从 commit body / remote_url 找）
   - 次选：commit body 里的文字描述
   - 兜底：只能推断时，**显式写"推断"+ 证据**，不许当成事实

**G7 门禁（必过）**：
- ✅ §1「🎯 做了什么」非空，且不是"本次提测 XX 改动"这种废话
- ✅ §1「📝 具体改动」按业务分组，每组至少 1 条证据 commit + 1 条代码注释引用
- ✅ §1「🤔 为什么改」有内容；如果 commit 里什么都没说，必须如实写"未找到明确动机，需开发补充"
- ❌ **禁**：§1 里只列技术清单（"改了 OrderService"），没有业务视角描述
- ❌ **禁**：§1 用"详见 §3 接口变更清单"这种偷懒甩锅

拒绝示例：
```
❌ 报告未生成。§1 业务改动段不合格：
  - 「🎯 做了什么」写的是"修改了订单服务"，这是技术描述不是业务描述
  - 「🤔 为什么改」为空，但 commit body 里没找到动机 —— 请补充 commit body 或 PR 描述
  - 「📝 具体改动」没引用任何代码注释证据
```

### STEP 0-B · 门禁 G1-G6（全过才能写文件）

| 门禁 | 触发条件 | 要求 | 不过 |
|---|---|---|---|
| G1 接口下游 | §2 接口变更非空 | 每行"下游影响"写具体名字，禁"无"/"未知"/"待定" | 列缺项，拒绝 |
| G2 SQL 完整 | `git diff --name-only` 命中 `*.sql` / `migrations/` / `schema/` | QA 版和开发版都要列全所有命中文件 | 列缺项，拒绝 |
| G3 脚本影响 | diff 命中 `scripts/` / `cmd/` / `cron/` / `job/` / `worker/` | 开发版 §3 每项展开（触发时机 + 失败后果 + 回滚） | 拒绝 |
| G4 自测完成 | 两个版本都有自测 checklist | 6 项全勾 + "自测发现的问题"栏填了 | 列未勾项，拒绝 |
| G5 真实性抽查 | 全部 | 挑 2 条接口 + 1 条 SQL，用 Grep 在代码里核对真实存在 | 对不上 = 造假，拒绝 |
| **G6 提测人** | 全部 | 提测人字段 = `git log -1 --format='%an <%ae>'` 结果；若用户手填了别的，以 git author 为准 + 在报告提一句"手填 X 被覆盖为 Y" | — |
| **G7 业务范围** | §1 业务改动段 | 按 STEP 0-D 流程挖掘；"做了什么"用业务视角，不是技术视角；必须带证据（commit hash + 代码注释引用） | 拒绝并列出不合格点 |
| **G8 开发自验**（**新**） | 开发版 §N 开发自验记录 | 按 STEP 0-E 三步走：理解摘要 + 3 个场景 + 真跑 dev 且有证据；任一"失败"未修不给生成 | 拒绝 |

**拒绝示例**：
```
❌ 报告未生成。缺少：
  - G1: §2 第 3 行 `/api/v1/xxx` 下游影响写了"无"，但这是修改接口，必须列出当前调用方（grep 结果）
  - G2: git diff 命中 migrations/20260423_03_foo.sql，QA 版和开发版都未列

请补充以上信息后重新执行「提测」。
```

## 两个文件的分工

### 📤 QA 版（给测试同学）
1. 概览（需求单 / 分支 / 提测人）
2. 🔌 接口变更清单（带下游影响）
3. 🗄️ SQL 数据影响（**简版**，不含上线顺序）
4. ✅ 开发自测报告（与开发版同步）

### 🛠️ 开发版（给程序员）
1. 概览（同步 QA 版）
2. 🗄️ SQL 上线顺序 & 回滚（**完整执行计划**）
3. ⚙️ 脚本/任务影响分析
4. 🧪 建议测试关注点（P0/P1/P2）
5. ✅ 开发自测报告（与 QA 版同步）
6. 🔍 真实性校验记录（OrangeCat 自动填 G1-G6）

两份都带同一个「提测概览」+ 同一个「自测 checklist」；其他内容按受众拆分。

## 模板文件

**只用相对路径**（不依赖任何外部 App / 本地配置）：

- `references/提测报告模板_QA版.md` —— QA 版报告基础结构
- `references/提测报告模板_开发版.md` —— 开发版报告基础结构

读模板时**始终相对本 Skill 目录**（不论它装在 `~/.claude/skills/orangecat/`、Cursor 的 skill 目录、还是 Claude Desktop 的内部存储）。**禁止**写绝对路径或假设任何宿主环境。

> 💡 给使用 Team Standards App 的同学：App 提供了图形化模板编辑器，编辑后「独立安装」时会把你的版本写到本 Skill 的 `references/` 下，覆盖默认版本。Skill 本身永远从 `references/` 读，不知道也不需要知道编辑器存在哪。

## 与单元测试相关

`✅ 5. 开发自测报告` 段的「跑单元测试，通过率」**必须填真实数字**：
- Go 项目跑 `go test -cover ./...`，把通过 / 总数填进去
- 某些核心 biz 无对应 `*_test.go` → 开发版 §4「建议测试关注点」必须把它标成 P0，让 QA 或下次迭代补

## 铁律

- **两个文件都要生成**，少一个即失败
- **提测人以 git author 为准**，手填只是初稿
- **不含 commit 列表 / 改动文件清单**（对 QA 无价值）
- 接口"下游影响"必具体
- 脚本影响说不清楚就拒绝生成
